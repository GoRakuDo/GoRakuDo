# ホームページ RPG 化 デザイン計画（語楽道クエスト）

**Date:** 2026-09-23
**Status:** 壁打ち合意済み・実装前
**Branch:** `feat/homepage-rpg`（このドキュメント以降の実装はここで行う）

## 0. 背景と目的

新ガイドページ（/panduan-immersion-...）は初心者向けに書いたが、**長すぎて読む人がほとんどいない**。
そこでホームページからRPGのように案内する体験に変え、「読ませる」から「進める」へ転換する。

**根本治療の原則**: 1画面=1アイデア、セリフは最大2〜3行。長文を絶対に出さない。

## 1. コンセプト

**「語楽道クエスト — 道（みち）を往く物語」**

「語楽道」の「道」そのものをゲームマップにする。ブランド名がすでに旅のメタファーなので、
RPG化は改名ではなく「名前の正体を現す」形になる。

**トーン**: 絵本っぽい優しい世界観 × 少年漫画っぽい冒険譚の熱さ（ミックス）。
絵柄は優しく、台詞は熱い。

## 2. ヒーロー選択（入口）

ホームページHeroで職業選択ではなく「あなたの現状は？」で3人から選ぶ:

- 🥚 完全初心者（ひらがなも読めない）
- 📖 教科書で停滞中（文法は知ってる、話せない）
- 📺 アニメ勢（聞き取りは多少できる）

**KISS の要点**: 選んだヒーローで**序章の台詞だけ**が変わる。本編シナリオは共通の1本道。
（全分岐にすると制作コスト3倍。序章だけ個別化で個人化の感動は確保する）

## 3. 章構成（シーン）

場面（背景絵）は**章ごとに1枚**。会話ビートごとに絵は変えない
（背景固定＋セリフが進む方がRPGらしい＆制作コスト抑制）。
章の切り替わり = マップ移動の演出。

| 章 | 内容 | RPG表現 | 既存コンテンツ対応 |
|---|---|---|---|
| 序章 | 覚醒 + **従来メソッドは失敗しがち**だと明白にする | SYSTEM NOTIFICATION（タイピングで開始） | 既存 AwakeningSection |
| 1章 | ⚔️ **分かれ道**: 教育型の道（暗い・茨・テスト地獄）vs 自然習得の道（光・育つ・赤ちゃんの言葉覚え方） | 文字通りの「分かれ道」シーン | 🆕 新規執筆 |
| 2章 | クラッシェンの伝承（自然なインプット = Comprehensible Input） | 道の先の賢者 / 魔法のレシピ (i+1) | Krashen / LAD / Rumus Ajaib |
| 3章 | 学習ロードマップ | スキルツリー（盆栽が育つ=レベルアップ） | Bonsai Roadmap / Stage群 |
| 4章 | ツール紹介 | 装備選択（Anki=武器、Yomitan=図鑑、asbplayer=修行場） | 既存 tools コンテンツ |
| 終章 | コミュニティ | ギルド入団 | Discord |

## 4. 演出

### タイピングアニメーション
- ドラクエ窓テキスト風のタイプライター表示（軽いJS）
- **タップ/クリックで全文表示（スキップ可）必須**
- `prefers-reduced-motion` 対応必須（即時全文表示）

### シーン遷移
- CSS scroll-driven animations + 軽いJS で制御
- 雰囲気演出（星空・ホタル等の粒子）は軽い canvas 1枚まで。それ以上はやらない

### 非採用: Three.js
2D絵本シーンに対してオーバースペック（600KB超・保守コスト大）。
CSS transform + パララックスで十分。KISS のため不採用。

## 5. 画像生成パイプライン（AI生成）

### 基本方針
- 生成は**制作時に1回だけ**。WebP で静的コミット（表示時生成ではない）
- シーン間で絵がブレないよう **スタイルガイド付きプロンプト雛形**を先に作る
  - 既存デザインとの整合: ダークな青紫の世界（OKLCHトークン準拠）に温かい光

### レイヤー構成（透過合成）
```
背景（章ごとに1枚・フルシーン）
  └ キャラスプライト（透過 WebP・複数配置可）
      └ 前景エフェクト（CSS粒子・光・枠）
```

分けるメリット:
- キャラだけ浮遊・スライドインできる（セリフ連動）
- 背景は同じまま**表情差分**で感情を出せる
- パララックス（背景とキャラのスクロール速度差）で立体感
- 背景の使い回しで制作コスト削減

### AI生成の実務
1. キャラは「単色背景で生成 → 背景除去（rembg等）」が最も安定
   （最初から透過生成は輪郭が汚れがち）
2. **同一キャラの一貫性**が最大の敵 → シード固定 or 参照画像付き生成
3. 透過形式は WebP（alpha対応・軽量）

### キャラクター計画
- キャラは**少数に絞る**: 案内役1人 + ヒーロー1人 が現実的（一貫性維持のため）
- 表情差分は MVP では1ポーズのみ。CSS の squash & stretch（伸縮）で
  「しゃべってる感」を出す。差分追加は後からでよい
- **未決**: 案内役キャラの造形（新造 vs 既存アート流用）

## 6. 技術構成

- Astro 静的生成のまま（ゲームエンジン不使用）
- ダイアログ内容は MDX または JSON データとして管理し、コンポーネントで描画
- シーン = コンポーネント、章遷移コントローラ = 軽いJSモジュール

## 7. 未決事項（実装前に決める）

   （推奨: まず専用ルートで作り、評価後にホームへ統合。既存ホームを壊さず作れる）
2. 案内役キャラの造形

## 8. 制作ロードマップ

1. **3a**: シナリオ叩き台（序章+1章のタイピング用セリフ、インドネシア語）
2. **3b**: シーン用コンポーネント（ダイアログボックス・シーンコンテナ・スクロール制御）
3. **3c**: ヒーロー選択 + マップUI
4. **画像生成**: スタイルガイド確立 → 章ごとの背景 + キャラスプライト
5. 統合・調整（このブランチで段階的に）
